## Overview

**Migration difficulty**: low. The new setting defaults to the behaviour described below, and nodes running either value interoperate: validators apply no rule of their own about how recently a message arrived, so consumption timing is a per-proposer choice. The one action to expect is a resync — see [Archiver database rebuild](#archiver-database-rebuild).

## New configuration

| Environment variable | Flag | Default | What it does |
| --- | --- | --- | --- |
| `SEQ_INBOX_L1_CONFIRMATIONS` | `--sequencer.inboxL1Confirmations` | `0` | How many L1 blocks must build on top of an L1-to-L2 message before this proposer consumes it. Only `0` and `1` are supported. |

### Choosing a value

`0` consumes a message as soon as your archiver sees it, so a bridged message reaches L2 in the next block your node builds. The cost is that an L1 reorg which changes the messages your node has already consumed costs your node that slot: the archiver drops the messages from the first one whose contents changed, along with the blocks built on them, and the checkpoint is abandoned. A reorg that re-mines the same messages in a different L1 block costs nothing — the archiver replaces only the bucket metadata derived from that block, the blocks that consumed the messages stand, and your node re-resolves the bucket it consumed by its contents before publishing. The exception is a re-mine that lands two buckets' messages in a single L1 block: the boundary between them stops existing, and the block that consumed through it goes, along with the blocks after it. At ten one-block L1 reorgs a day, with messages present in 30% of L1 blocks, that puts an upper bound of roughly 0.13% on the slots your node loses — about three a day across the whole network, and only for the reorgs that reorder a message, drop one, or merge two buckets into one. Nothing else is affected: the chain carries on and the message is consumed by the next proposer.

`1` consumes a message only once a child block is observed on top of the one carrying it, or the following L1 slot was missed and the block is still canonical after it. That removes the lost slots above and adds roughly one Ethereum slot (~12s) of latency to every bridged message.

The sandbox and any node running the automine sequencer ignore this setting and always consume immediately, since their L1 mines on demand.

### What validators check

A validator does not check how recently a message arrived; it checks what L1 checks, plus that the Inbox contents a proposal references match its own view of the Inbox. So a proposer running either value collects attestations from validators running either value. The exception is the moment of an L1 reorg, where a proposer and a validator can briefly disagree about the Inbox itself; the validator forces an archiver sync and re-checks before rejecting.

## Archiver database rebuild

The archiver's on-disk schema changed, so the first start on v6.0.0 discards the local archiver database and resyncs it from L1. No action is required, but allow for the resync when planning the upgrade: the node serves stale data until it catches up, and a node that is also a validator should not be expected to attest during that window.
