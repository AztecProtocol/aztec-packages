## Overview

**Migration difficulty**: high, mostly because almost everything you pull from moved.

v6 is a hard fork: it is a complete new deployment starting from genesis, not an upgrade
of the existing chain. You are standing up a new node against a new network rather than
migrating an existing one, so there is no state to carry over and nothing to resync.

Two things to settle before you start: every artifact location changed, and the
`ACVM_*` configuration variables were renamed with no fallback. A node doing real
proving fails to start on the old names; one that is not falls back to WASM
simulation and starts anyway, much slower, so a clean startup is not evidence that
your configuration migrated.

:::info v6.0.0-rc.1 is Testnet only
`v6.0.0-rc.1` is for **Testnet**. Do not run it on Mainnet. The first v6 release for
Mainnet will be the `v6.0.0` stable release.
:::

## New repository, image and package locations

Everything moved. Old locations keep what was already published, so existing v5 setups
keep working, but nothing new lands there.

| | v5 and earlier | v6 |
| --- | --- | --- |
| Source repository | `AztecProtocol/aztec-packages` | `aztec-labs-eng/aztec-node` |
| Docker images | `aztecprotocol/aztec` | `azteclabs/aztec` |
| Prover agent image | `aztecprotocol/aztec-prover-agent` | `azteclabs/aztec-prover-agent` |
| npm (client packages) | `@aztec/*` | `@aztec-labs/*` |
| npm (foundation packages) | `@aztec/bb.js`, `@aztec/noir-*` | `@aztec-foundation/*` |
| Aztec.nr | in the monorepo | `aztec-labs-eng/aztec-nr` |

Update your image references first. A compose file or Helm values still pointing at
`aztecprotocol/aztec` will pull a v5 image and fail against a v6 network.

```diff
- image: aztecprotocol/aztec:5.2.0
+ image: azteclabs/aztec:6.0.0-rc.1
```

The `@aztec` npm scope keeps the packages published for earlier versions, so an existing
project pinned to a v5 version continues to resolve. The packages now depend on upstream
`viem` instead of the `@aztec/viem` fork.

## Behaviour changes

### `ACVM_*` configuration renamed to `NOIR_EXECUTE_*`

Protocol circuits are now executed with noir's `noir-execute` rather than the `acvm`
binary, and the configuration naming the executor follows the tool. What you point it at
is unchanged.

| Old | New |
| --- | --- |
| `ACVM_BINARY_PATH` | `NOIR_EXECUTE_BINARY_PATH` |
| `ACVM_WORKING_DIRECTORY` | `NOIR_EXECUTE_WORKING_DIRECTORY` |
| `--sequencer.acvmBinaryPath` | `--sequencer.noirExecuteBinaryPath` |
| `--sequencer.acvmWorkingDirectory` | `--sequencer.noirExecuteWorkingDirectory` |
| `--proverNode.acvmBinaryPath` | `--proverNode.noirExecuteBinaryPath` |
| `--proverNode.acvmWorkingDirectory` | `--proverNode.noirExecuteWorkingDirectory` |

```diff
- ACVM_BINARY_PATH=/usr/src/labs-aztec-toolchain/bin/noir-execute
- ACVM_WORKING_DIRECTORY=/usr/src/acvm
+ NOIR_EXECUTE_BINARY_PATH=/usr/src/labs-aztec-toolchain/bin/noir-execute
+ NOIR_EXECUTE_WORKING_DIRECTORY=/usr/src/noir-execute
```

**There is no fallback to the old names.** A prover agent exits with `Requested real
proving but no path to bb or noir-execute binaries provided`; a prover node or sequencer
configured for real proofs throws from `BBNativeRollupProver.new` when it tries to stat
an undefined path. Only a node running without real proofs survives, by falling back to
WASM simulation, which is much slower, so a node that appears to start may still be
badly degraded.

If you run the release image it sets the new variables itself, and its default working
directory moves from `/usr/src/acvm` to `/usr/src/noir-execute`. Check any values you
override.

### Attester-initiated sequencer exits

A position can now be exited by its attester rather than only by the registered
withdrawer, and exits can be batched: one relayed transaction instead of one per
position. That is the point for anyone running tens or hundreds of delegations.

Three functions are live on the rollup:

| Function | What it does |
| --- | --- |
| `initiateWithdrawByAttester(address)` | Exit one position. Caller must be the attester. |
| `initiateWithdrawByAttesterBatch(...)` | Relay many attester-signed exits. Reverts if any entry is invalid. |
| `initiateWithdrawByAttesterBatchUpToLimit(...)` | Same, but processes the largest permitted prefix instead of reverting. |

:::info CLI wrappers from v6.0.0-rc.3
The `aztec initiate-withdraw-by-attester`, `initiate-withdraw-by-attester-batch` and
`sign-attester-exit` commands ship from the `v6.0.0-rc.3` toolchain. On `v6.0.0-rc.1`
they are missing: call the functions directly, as below.
:::

#### Calling the contract directly

Exit a single position, signed and submitted by the attester:

```bash
cast send $ROLLUP "initiateWithdrawByAttester(address)" $ATTESTER \
    --private-key $ATTESTER_KEY --rpc-url $L1_RPC
```

Batching needs an EIP-712 signature per attester. The domain is
`{ name: "Aztec Rollup", version: "1", chainId: <L1 chain id>, verifyingContract: <rollup> }`
and the type is `AttesterExit(address attester,uint256 deadline)`. Sign one per position:

```bash
cast wallet sign --private-key $ATTESTER_KEY --data '{
  "domain":{"name":"Aztec Rollup","version":"1","chainId":'$L1_CHAIN_ID',"verifyingContract":"'$ROLLUP'"},
  "types":{"AttesterExit":[{"name":"attester","type":"address"},{"name":"deadline","type":"uint256"}]},
  "primaryType":"AttesterExit",
  "message":{"attester":"'$ATTESTER'","deadline":"'$DEADLINE'"}
}'
```

Then relay them. Each entry is `(attester, deadline, (v, r, s))`, and the relayer pays
the gas, so the submitting key need not be an attester:

```bash
cast send $ROLLUP \
    "initiateWithdrawByAttesterBatchUpToLimit((address,uint256,(uint8,bytes32,bytes32))[])" \
    "[($ATTESTER_0,$DEADLINE,($V0,$R0,$S0)),($ATTESTER_1,$DEADLINE,($V1,$R1,$S1))]" \
    --private-key $RELAYER_KEY --rpc-url $L1_RPC
```

`deadline` is a unix timestamp and must be in the future. Each attester may appear only
once per batch. Prefer the `UpToLimit` variant for large batches: the plain
`initiateWithdrawByAttesterBatch` reverts the whole transaction if any single entry is
rejected, losing the gas for the rest.

Withdrawer-initiated exits are unchanged.

### Publishers must afford the L1 transaction before work starts

Nodes now check that a publisher holds enough ETH for its L1 transaction before doing
the work behind it. The amount checked is a worst case: the transaction's gas limit
times the max fee per gas, plus blob fees, at current L1 fees. At a 1 gwei base fee a
proposal needs a few thousandths of an ETH.

- **Sequencers**: if no publisher for the proposer can afford a checkpoint proposal,
  the node skips the slot before building or gossiping anything. It logs an error with
  each publisher's balance and the required amount, and records the
  `insufficient_publisher_balance` reason on
  `aztec.sequencer.checkpoint.precheck_failed_count`. Governance and slashing votes are
  still attempted. If a publisher can afford the proposal but not the votes bundled
  with it, the votes are dropped and the proposal is sent alone.
- **Provers**: a prover node still proves an epoch while no publisher can afford the
  proof submission, but holds the finished proof back instead of sending it. It
  retries every 12 seconds and submits as soon as a publisher is funded, until the
  proof submission window closes. `aztec.prover_node.proof_submission_unaffordable_count`
  counts the held back proofs. Nothing changes when proof publishing is disabled.
- **Selection**: a publisher with a recently mined transaction is no longer ranked
  below an idle one with less ETH, so a dust-funded idle publisher can no longer win
  every proposal. A publisher whose transaction was rejected for insufficient funds is
  skipped until its balance increases, or for at most five minutes.

### Publisher balances are checked every minute

Sequencers and prover nodes now read every publisher's balance once a minute, whether
or not the publisher has sent anything, and price a reference transaction at current
L1 fees: the first checkpoint proposal of an epoch for a sequencer, an epoch proof
submission for a prover. At startup the node logs a `Publisher balances` line with
every publisher's balance, at error level if none can afford the reference
transaction. While that lasts, it logs `No publisher can afford a proposal` (or
`an epoch proof`) at most every 10 minutes, naming the publisher to fund and how
much ETH it is missing. The skipped proposal and held back proof errors name them too.

A warning is logged when a publisher's balance falls below a multiple of the cost of
the reference transaction:

```bash
--sequencer.publisherLowBalanceWarningMultiplier <value>    ($PUBLISHER_LOW_BALANCE_WARNING_MULTIPLIER)
--proverNode.publisherLowBalanceWarningMultiplier <value>   ($PUBLISHER_LOW_BALANCE_WARNING_MULTIPLIER)
```

The default is `4`. If you use [automatic top-ups](/operate/operators/solo-sequencer/fund-accounts#optional-automatic-top-ups),
set `PUBLISHER_FUNDING_THRESHOLD` above the warning level; the node warns if it is not.
Top-ups are now checked every minute instead of every 2 minutes.

Metric changes (Prometheus names):

- `aztec_l1_publisher_balance_eth` is now recorded every minute for every publisher,
  instead of only after a transaction is sent. Alerts on it now fire for a publisher
  that has never sent, or stopped sending because it cannot afford to. It gains an
  `aztec_l1_tx_scope` label (`sequencer` or `prover`).
- New `aztec_l1_publisher_sends_affordable`: how many reference transactions each
  publisher's balance covers at current fees. Alert when it drops below 1.
- New `aztec_l1_publisher_required_balance_eth`: the cost of one reference transaction
  at current fees.
- New `aztec_l1_publisher_funder_balance_eth`: the balance of the funding account used
  for automatic top-ups.
- `aztec_l1_balance_eth` is deprecated and will be removed in a later release. Use
  `aztec_l1_publisher_balance_eth` instead.
- `aztec_l1_gas_price_wei` and `aztec_l1_blob_base_fee_wei` are now exported. They were
  defined before but never reached the exporter.

See [Metrics reference](/operate/operators/monitoring/metrics-reference#l1-publisher-eth-balance)
for example alert rules.

## New node RPC methods

Two additions to the JSON-RPC surface. Both are additive; nothing was removed.

| Method | What it is for |
| --- | --- |
| `aztec_getTxEffectMembershipWitness` | Membership proof for a transaction's effects. |
| `aztec_getValidatorStatsBatch` | Validator statistics for several attesters in one call. |

Both currently render under "Other methods" in the
[node API reference](/operate/operators/reference/node_api_reference) because the
generator has no grouping for them yet.

## Upgrade checklist

1. Point your image references at `azteclabs/aztec` and `azteclabs/aztec-prover-agent`.
2. Rename `ACVM_*` to `NOIR_EXECUTE_*` in your environment, compose files or Helm values,
   **before** starting a v6 node.
3. Confirm any overridden working directory matches the new default if you rely on the
   release image.
4. Take the L1 contract addresses and the RPC endpoint for the network you are joining
   from [networks.md](/networks). v6 is a new deployment, so none of the v5 values carry
   over.
5. Fund your sequencer and prover publishers. A node whose publishers cannot afford the
   L1 transaction skips the proposal or holds back the proof submission. Alert on
   `aztec_l1_publisher_sends_affordable`, and move any alert or dashboard on
   `aztec_l1_balance_eth` to `aztec_l1_publisher_balance_eth`.
