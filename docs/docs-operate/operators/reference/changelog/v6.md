## Overview

**Migration difficulty**: low. No action is required. The new setting defaults to the behaviour described below, and nodes running either value interoperate: validators accept whatever L1 accepts, so consumption timing is a per-proposer choice and never a reason to reject a proposal.

## New configuration

| Environment variable | Flag | Default | What it does |
| --- | --- | --- | --- |
| `SEQ_INBOX_L1_CONFIRMATIONS` | `--sequencer.inboxL1Confirmations` | `0` | How many L1 blocks must build on top of an L1-to-L2 message before this proposer consumes it. Only `0` and `1` are supported. |

### Choosing a value

`0` consumes a message as soon as your archiver sees it, so a bridged message reaches L2 in the next block your node builds. The cost is that a one-block L1 reorg can move the message out from under a checkpoint your node has already built, and that checkpoint is then abandoned. At ten one-block L1 reorgs a day, with messages present in 30% of L1 blocks, this loses roughly 0.07% of the slots your node proposes — about one or two slots a day across the whole network — and nothing else: the chain is unaffected and the message is consumed by the next proposer.

`1` consumes a message only once another L1 block has built on top of the one carrying it. That removes the lost slots above and adds roughly one Ethereum slot (~12s) of latency to every bridged message.

The sandbox and any node running the automine sequencer ignore this setting and always consume immediately, since their L1 mines on demand.
