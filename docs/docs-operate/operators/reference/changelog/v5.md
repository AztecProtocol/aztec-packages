## Overview

**Migration difficulty:** low. No action is required unless you tune validator signing timeouts.

## New features

### Configurable timeout for validator signing operations

```bash
$VALIDATOR_SIGNING_OPERATION_TIMEOUT_MS    (default: 30000)
```

Each signing operation performed by a validator (block proposals, attestations) now has a hard upper
bound. If the signer — including a remote Web3Signer — does not return within this time, the
operation is aborted, the slashing-protection lock for the duty is released, and the signing attempt
fails so it can be safely retried. Keep this value well below
`VALIDATOR_HA_MAX_STUCK_DUTIES_AGE_MS` (default 144000); the node logs a warning at startup if it is
not. This is distinct from `VALIDATOR_HA_SIGNING_TIMEOUT_MS`, which controls how long a node waits
for *another* node's in-progress signing in high-availability setups.

Requests to a remote Web3Signer are additionally bounded by a 30-second HTTP timeout instead of
hanging indefinitely.

## Behavioral changes

### Signing fails instead of broadcasting when the slashing-protection record is lost

Previously, if a validator's slashing-protection record for a duty was removed while signing was in
flight (for example by the stuck-duty cleanup during a long remote-signer stall), the node logged a
warning but still broadcast the signature — leaving the duty unprotected against a later
conflicting signature. The node now treats this as a signing failure and does not broadcast,
eliminating a double-sign (slashing) risk. Operators may see `SigningLockLostError` in logs where
the old warning appeared; the duty is safe to retry.

### Postgres connection errors no longer crash high-availability validators

Validators running with `VALIDATOR_HA_SIGNING_ENABLED=true` no longer exit when an idle connection
to the slashing-protection database errors (for example during a Postgres restart or failover). The
error is logged and the connection pool recovers on its own.
