## Single-server compose

Create `docker-compose.yml` in your `aztec-sequencer/` directory:

<ConfigCode language="yaml" title="docker-compose.yml">{`services:
  aztec-sequencer:
    image: "aztecprotocol/aztec:{{IMAGE_TAG}}"
    container_name: "aztec-sequencer"
    ports:
      - "\${AZTEC_PORT}:\${AZTEC_PORT}"
      - "\${P2P_PORT}:\${P2P_PORT}"
      - "\${P2P_PORT}:\${P2P_PORT}/udp"
    volumes:
      - \${DATA_DIRECTORY}:/var/lib/data
      - \${KEY_STORE_DIRECTORY}:/var/lib/keys:ro
    environment:
      DATA_DIRECTORY: /var/lib/data
      KEY_STORE_DIRECTORY: /var/lib/keys
      LOG_LEVEL: \${LOG_LEVEL}
      ETHEREUM_HOSTS: \${ETHEREUM_HOSTS}
      L1_CONSENSUS_HOST_URLS: \${L1_CONSENSUS_HOST_URLS}
      ETHEREUM_DEBUG_HOSTS: \${ETHEREUM_DEBUG_HOSTS}
      P2P_IP: \${P2P_IP}
      P2P_PORT: \${P2P_PORT}
      AZTEC_PORT: \${AZTEC_PORT}
      AZTEC_ADMIN_PORT: \${AZTEC_ADMIN_PORT}
    entrypoint: >-
      node
      --no-warnings
      /usr/src/yarn-project/aztec/dest/bin/index.js
      start
      --node
      --sequencer
      --network {{NETWORK_NAME}}
    networks:
      - aztec
    restart: always
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://localhost:'+process.env.AZTEC_PORT,{method:'POST',headers:{'content-type':'application/json'},body:JSON.stringify({jsonrpc:'2.0',method:'aztec_getChainTips',params:[],id:1})}).then(r=>r.json()).then(j=>{var b=j&&j.result&&j.result.proven&&j.result.proven.block;var n=b&&b.number;if(typeof n!=='number'||n<=0)process.exit(1);return fetch('http://localhost:'+process.env.AZTEC_PORT,{method:'POST',headers:{'content-type':'application/json'},body:JSON.stringify({jsonrpc:'2.0',method:'aztec_getSyncedL1Timestamp',params:[],id:1})}).then(r=>r.json()).then(j2=>{var ts=Number(j2&&j2.result);if(!ts||(Math.floor(Date.now()/1000)-ts)>300){process.exit(1)}process.exit(0)})}).catch(()=>process.exit(1))"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 10m

networks:
  aztec:
    name: aztec`}</ConfigCode>

## HA compose: same attester, two nodes, shared PostgreSQL

In HA mode you run **two near-identical sequencer nodes**, both holding the same attester key. They coordinate via a shared PostgreSQL database that ensures only one node signs each duty (block proposal, attestation, governance vote). If one node dies, the other keeps attesting without missing a duty and without risking double-signing.

You'll need:

1. A PostgreSQL database reachable by both nodes. Use a managed multi-zone service with automatic failover; a database on a single machine takes both nodes down with it. See [the HA database setup](/operate/operators/setup/high_availability_sequencers#step-6-set-up-the-ha-database) for provider examples.
2. The HA database schema initialized once before starting either node:

<ConfigCode language="bash">{`aztec migrate-ha-db up --database-url postgresql://user:password@host:5432/validator_ha`}</ConfigCode>

3. The compose file below, deployed to **both servers** with **different `VALIDATOR_HA_NODE_ID` values** (and different `P2P_IP` values per server's public IP). Everything else stays identical.

<ConfigCode language="yaml" title="docker-compose.yml (deploy on both servers)">{`services:
  aztec-sequencer:
    image: "aztecprotocol/aztec:{{IMAGE_TAG}}"
    container_name: "aztec-sequencer"
    ports:
      - "\${AZTEC_PORT}:\${AZTEC_PORT}"
      - "\${P2P_PORT}:\${P2P_PORT}"
      - "\${P2P_PORT}:\${P2P_PORT}/udp"
    volumes:
      - \${DATA_DIRECTORY}:/var/lib/data
      - \${KEY_STORE_DIRECTORY}:/var/lib/keys:ro
    environment:
      DATA_DIRECTORY: /var/lib/data
      KEY_STORE_DIRECTORY: /var/lib/keys
      LOG_LEVEL: \${LOG_LEVEL}
      ETHEREUM_HOSTS: \${ETHEREUM_HOSTS}
      L1_CONSENSUS_HOST_URLS: \${L1_CONSENSUS_HOST_URLS}
      ETHEREUM_DEBUG_HOSTS: \${ETHEREUM_DEBUG_HOSTS}
      P2P_IP: \${P2P_IP}
      P2P_PORT: \${P2P_PORT}
      AZTEC_PORT: \${AZTEC_PORT}
      AZTEC_ADMIN_PORT: \${AZTEC_ADMIN_PORT}
      # HA coordination
      VALIDATOR_HA_SIGNING_ENABLED: "true"
      VALIDATOR_HA_DATABASE_URL: \${VALIDATOR_HA_DATABASE_URL}
      VALIDATOR_HA_NODE_ID: \${VALIDATOR_HA_NODE_ID}
    entrypoint: >-
      node
      --no-warnings
      /usr/src/yarn-project/aztec/dest/bin/index.js
      start
      --node
      --sequencer
      --network {{NETWORK_NAME}}
    networks:
      - aztec
    restart: always
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://localhost:'+process.env.AZTEC_PORT,{method:'POST',headers:{'content-type':'application/json'},body:JSON.stringify({jsonrpc:'2.0',method:'aztec_getChainTips',params:[],id:1})}).then(r=>r.json()).then(j=>{var b=j&&j.result&&j.result.proven&&j.result.proven.block;var n=b&&b.number;if(typeof n!=='number'||n<=0)process.exit(1);return fetch('http://localhost:'+process.env.AZTEC_PORT,{method:'POST',headers:{'content-type':'application/json'},body:JSON.stringify({jsonrpc:'2.0',method:'aztec_getSyncedL1Timestamp',params:[],id:1})}).then(r=>r.json()).then(j2=>{var ts=Number(j2&&j2.result);if(!ts||(Math.floor(Date.now()/1000)-ts)>300){process.exit(1)}process.exit(0)})}).catch(()=>process.exit(1))"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 10m

  aztec:
    name: aztec`}</ConfigCode>

In each server's `.env`, add:

```bash
VALIDATOR_HA_DATABASE_URL=postgresql://user:password@host:5432/validator_ha
VALIDATOR_HA_NODE_ID=validator-node-1   # use validator-node-2 on the second server
```

:::warning Same keystore on both nodes
Both nodes hold the same attester key. The shared Postgres lock is what stops them from both signing the same duty. Do not run HA without the database, or you risk double-signing and slashing.
:::

:::info What HA does and doesn't do
HA gives you **redundancy for one attester identity**. If you have N validator identities and want to spread them across multiple nodes for load (rather than redundancy), that's a different setup, not what this section covers. See [High availability sequencers](/operate/operators/setup/high_availability_sequencers) for the canonical reference, including remote-signer patterns and database tuning.
:::

:::info Health check
The `healthcheck` block probes the node's own HTTP API every 30 seconds. The container reports:

- **`starting`** during initial sync. The node answers its API but does not yet have a proven block, so the check holds off. The `start_period` of 10 minutes covers the snapshot download and catch-up before any failure counts. If your node typically takes longer to reach a proven tip, raise `start_period` to match.
- **`healthy`** once the node has a proven tip greater than 0 and the chain time it has synced to is within 5 minutes of now, meaning it is keeping up with network state.
- **`unhealthy`** if the API stops answering, the node falls more than 5 minutes behind the chain, or the proven tip drops back to 0 for three checks in a row.

The status shows in `docker compose ps` and can be scraped by monitoring. The check **reports** health; it does not restart the container on its own. For automatic recovery on `unhealthy`, pair it with a tool such as `autoheal`, or alert on the status from your monitoring stack.

The check requires both a proven L2 tip greater than 0 and a recent synced chain time (within 5 minutes), so it catches a node that synced once and then stalled. Adjust the `300` (seconds) in the probe to change that staleness window.
:::

:::warning Admin port stays internal
Port 8880 is the admin port and is intentionally not mapped to the host. Reach it only via `docker exec` on the box itself.
:::
