# State Models: Notes, Nullifiers, and Commitments

## The Challenge of Private State

In traditional blockchains, state is simple:
- Values are stored directly in the state tree
- Everyone can read the current state
- Updates modify values in place

For privacy, we need state that:
- Hides values from observers
- Prevents linking between transactions
- Still allows valid computation and verification

Enter the **note-based state model**.

## Notes: Private State Containers

### What is a Note?

A **note** is like a private data container - think of it as an encrypted envelope containing:
- **Value:** Some data (amount, content, etc.)
- **Owner:** Who can access this note
- **Metadata:** Additional context needed for the application

```
📋 Example Note:
├── Value: 50 ETH
├── Owner: Alice's public key
├── Nonce: Random value for uniqueness
└── Encryption: Only Alice can read the contents
```

### Note Lifecycle

Notes follow a simple lifecycle:

```
Creation → Storage → Discovery → Spending → Nullification

1. Creation: New note generated by a transaction
2. Storage: Note commitment stored in public tree
3. Discovery: Note owner finds and decrypts their note
4. Spending: Note used as input to another transaction  
5. Nullification: Note marked as spent (can't be used again)
```

## Commitments: Public Fingerprints

### What is a Commitment?

A **commitment** is a cryptographic hash of a note - like a fingerprint that proves the note exists without revealing its contents.

```
Note (Private):
├── Value: 50 ETH
├── Owner: Alice
└── Nonce: abc123

Commitment (Public):
└── Hash: 0x7a9f3c... (cryptographic hash of the note)
```

### Why Use Commitments?

**Privacy:** The commitment reveals nothing about the note's contents
**Integrity:** You can't change the note without changing the commitment  
**Existence:** The commitment proves a valid note was created
**Uniqueness:** Each note has a unique commitment

### The Note Hash Tree

All note commitments are stored in a public **Note Hash Tree** (append-only):

```
Note Hash Tree:
├── 0x1a2b3c... (commitment to some note)
├── 0x4d5e6f... (commitment to another note)
├── 0x7a9f3c... (commitment to Alice's 50 ETH note)
└── 0x8b1c4d... (commitment to yet another note)
```

**Everyone can see:** The tree of commitments
**Nobody can see:** What notes the commitments represent (unless they own them)

## Nullifiers: Preventing Double-Spending

### The Double-Spending Problem

If notes are private, how do we prevent someone from spending the same note twice?

```
Problem Scenario:
├── Alice has a note worth 50 ETH
├── Alice spends the note to pay Bob 50 ETH
├── Alice tries to spend the same note again to pay Carol 50 ETH
└── How do we detect this without revealing Alice's notes?
```

### What is a Nullifier?

A **nullifier** is a unique identifier for a spent note - like a "void" stamp that prevents reuse.

```
When Alice spends her note:
├── Creates: Nullifier = Hash(note + Alice's secret key)
├── Publishes: The nullifier publicly
└── Result: This note can never be spent again
```

### Key Properties of Nullifiers

**Uniqueness:** Each note produces a unique nullifier when spent
**Unlinkability:** The nullifier doesn't reveal which note was spent
**Verifiability:** Anyone can verify a nullifier was created correctly
**Prevention:** The same note can't create two different valid nullifiers

### The Nullifier Tree

All nullifiers are stored in a public **Nullifier Tree**:

```
Nullifier Tree:
├── 0x9f8e7d... (nullifier for some spent note)
├── 0x6c5b4a... (nullifier for another spent note)  
├── 0x3a2b1c... (nullifier for Alice's spent note)
└── 0x7d6e5f... (nullifier for yet another spent note)
```

When validating a new transaction:
1. Check if the nullifier already exists in the tree
2. If yes: reject (double-spending attempt)
3. If no: accept and add nullifier to tree

## Putting It All Together: Note-Based Privacy

### Private Transaction Flow

Let's trace a private transaction from Alice to Bob:

#### Step 1: Alice's Initial State
```
Alice's Private Notes:
└── Note1: 100 ETH (commitment 0x1a2b3c... in Note Hash Tree)

Public State:
├── Note Hash Tree: [..., 0x1a2b3c..., ...]
└── Nullifier Tree: [existing nullifiers...]
```

#### Step 2: Alice Sends 30 ETH to Bob  
```
Alice's Transaction:
├── Input: Note1 (100 ETH) - will be spent
├── Outputs: 
│   ├── New note for Bob: 30 ETH
│   └── Change note for Alice: 70 ETH
├── Creates: Nullifier for Note1
└── Generates: Proof of valid transaction
```

#### Step 3: Updated State
```
Alice's Private Notes:
└── Note2: 70 ETH (change note)

Bob's Private Notes:
└── Note3: 30 ETH (received from Alice)

Public State:
├── Note Hash Tree: [..., commitment to Note2, commitment to Note3, ...]
└── Nullifier Tree: [..., nullifier for Note1, ...]
```

### What Outside Observers See

**Public Information:**
- New commitments appeared in Note Hash Tree
- New nullifier appeared in Nullifier Tree
- A valid zero-knowledge proof was submitted

**Private Information (hidden):**
- Which notes were spent
- How much value was transferred
- Who received the notes
- The relationship between inputs and outputs

## State Model Comparison

### Traditional (Account-Based) State

```
Global State:
├── Alice: 100 ETH ← Everyone sees this
├── Bob: 50 ETH   ← Everyone sees this
└── Carol: 75 ETH ← Everyone sees this

Transaction: Alice → Bob (30 ETH)
├── Alice: 100 - 30 = 70 ETH ← Everyone sees this
└── Bob: 50 + 30 = 80 ETH     ← Everyone sees this
```

### Privacy-Preserving (Note-Based) State

```
Public Trees:
├── Note Hash Tree: [encrypted commitments]
└── Nullifier Tree: [spent note identifiers]

Alice's Private View:
├── Note1: 100 ETH (she can decrypt)
└── After transaction: Note2: 70 ETH (change)

Bob's Private View:
├── Previous notes: [his other notes]
└── After transaction: Note3: 30 ETH (received)

Outside Observer View:
├── Sees: New commitments and nullifiers
└── Doesn't know: Amounts, ownership, or relationships
```

## Key Mental Shifts

### From Direct State to Encrypted Containers

**Old Thinking:**
- "Store the balance directly in the state tree"
- "Read the current balance from storage"

**New Thinking:**
- "Create encrypted notes containing the value"
- "Sum up my decryptable notes to know my balance"

### From State Updates to Note Lifecycle

**Old Thinking:**
- "Update Alice's balance: subtract 30"
- "Update Bob's balance: add 30"

**New Thinking:**
- "Spend Alice's note (nullify it)"
- "Create new notes for Bob and Alice (change)"

### From Public Verification to Proof-Based Validation

**Old Thinking:**
- "Check that Alice had enough balance"
- "Verify the arithmetic is correct"

**New Thinking:**
- "Verify Alice's proof that she owns the input note"
- "Verify the proof that outputs equal inputs"

## Key Takeaways

1. **Notes are private state containers** - encrypted data only owners can read
2. **Commitments are public fingerprints** - prove notes exist without revealing contents
3. **Nullifiers prevent double-spending** - unique identifiers for spent notes
4. **Privacy comes from encryption + unlinkability** - observers can't connect notes to owners or transactions
