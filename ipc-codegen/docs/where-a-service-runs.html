Where a service runs

An instance is the in-process version of a server process. Out of process you get one by spawning a process; in process you get one with the library's _create(). Everything else follows from that.

Instance = process

An instance has its own state, takes one Init, and answers any number of callers. A server process is exactly that, so a service can be moved between the two without its callers seeing a difference beyond how they reach it.

Several callers can share one instance either way: the TS world state client and every simulator use the one wsdb. Whether an instance takes overlapping calls is the service's choice. bb and wsdb-ref take one at a time; aztec-wsdb takes calls from many threads at once and orders them per fork.

The one difference

A process gets its own threads, memory and environment. Instances in one process share the host's. A setting read from the environment is therefore per process: the threads option is exported to a spawned process as HARDWARE_CONCURRENCY and RAYON_NUM_THREADS, and in process it is the host's, or the wasm module's own thread count. Everything else a service needs is in its Init, as all of aztec-wsdb's configuration is.

One factory

A C++ service defines one function, make_service(), which returns its instance. The generated serve() calls it once for the process, and the generated _create() calls it once per instance, so both placements run the same code. In a process, serve() also routes the instance's host calls to the paths its --host-call arguments name.

What carries a call

Every call is the same msgpack request in and response out. Only the crossing differs.

In process, each service exports <svc>_ipc_ffi_create, _call, _destroy, _alloc, _free and, natively, _set_host_call. A .so, a static archive and a wasm module all export the same functions.

Appendix: which thread runs it

A sync backend blocks its caller until the response; an async one returns a promise. Where the instance runs follows from that.
