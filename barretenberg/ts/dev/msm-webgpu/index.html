BN254 MSM: WebGPU vs barretenberg WASM

Runs an MSM of the first n = 2log₂(n) points of the public BN254 G1 SRS against fresh random Fr scalars and times two implementations on the same input: (1) WebGPU MSM via this repo's MsmV2 pair-tree pipeline, and (2) barretenberg WASM Pippenger multi-threaded (the threaded WASM with all hardware threads). The WASM path calls the bb_native_pippenger_bn254_* exports, which skip the BBERG_WEBGPU_MSM_HOOK delegation so we measure the in-tree Pippenger and not the bridge round-trip.

At log₂(n) = 16 the GPU result is cross-checked against bn254.G1.ProjectivePoint.msm from @noble/curves for correctness; at all sizes the both implementations are cross-checked against each other. The SRS (up to 220 points) is fetched from crs.aztec-cdn.foundation on first page load, decompressed in JS, and cached in IndexedDB — cold pull is slow (~2.5 min); reloads are instant. Multi-threaded WASM requires cross-origin isolation (COOP/COEP set by the dev server) for SharedArrayBuffer.

(n = 65536)

Default mode is WebGPU-only. Setting COOP/COEP unconditionally was observed to break the WebGPU MSM in this dev page, so the dev server only emits those headers when the URL carries ?coi=1. Without cross-origin isolation, SharedArrayBuffer is unavailable and the threaded barretenberg WASM can't load — so the WASM-using buttons (Run, Run × 5, Sweep) are disabled. Click Enable WASM (reload with COI) to reload with the headers turned on.

Recommended order on a fresh load: (1) Quick sanity check first — runs one WebGPU MSM at log₂(n)=16 with no WASM, no workers, no bigint pippenger. If that hangs, the problem is WebGPU or the SRS, and stopping here saves you from spawning anything heavier. (2) Click Enable WASM (the page reloads with COI). Then Run at log₂(n)=16 — adds WASM (boots ~4 pthread workers) and runs all three paths once. Hit Stop at any time to terminate the workers. (3) Bump sizes / Sweep only after the smaller paths look healthy.

Notes: navigator.hardwareConcurrency on this machine reports ?; the threaded WASM forks one OS thread per "MT threads" slot. The WASM boots lazily on first use and stays alive until Stop destroys it. The noble check is off by default because its bigint Pippenger blocks the main thread for many seconds (no yields possible).

What this is testing

Inputs: the first n G1 points of the public BN254 SRS (real prover bases — same source that bb.js hands to the WASM prover), and n random Fr scalars from crypto.getRandomValues.

GPU side: pack points into the [x_0|y_0|x_1|y_1|...] interleaved LE-32 layout the port expects (matches the C++ marshal_points marshalling — see webgpu_msm_marshalling.hpp), scalars into n × 32 LE bytes, then build an MsmV2Pool + MsmV2 and run it.

Noble reference (correctness, log₂(n) = 16 only): noble's ProjectivePoint.msm(...) Pippenger over the same points and scalars; comparison is on the affine (x, y) pair. Skipped at larger sizes because the bigint Pippenger takes minutes per call.

WASM Pippenger (timing, MT): copies the byte buffers into the WASM heap (bbmalloc + writeMemory) and decodes them into the native point/scalar vectors via bb_native_pippenger_bn254_load — all untimed. The timed call is bb_native_pippenger_bn254_run(num_threads, result), which runs batch_multi_scalar_mul_native over the loaded inputs with num_threads = navigator.hardwareConcurrency. Only Pippenger compute is measured; input-buffer population is excluded from the wall-time.
