Why GPU?

MSM is embarrassingly parallel:

  • $n$ independent point additions
  • $n \cdot T$ independent digit extractions
  • $\sim n$ independent affine adds per round (in batch-affine SMVP)
  • $T \cdot W$ independent partial reductions in BPR

CPU (WASM-MT, 14 threads)

~14× wide

Each thread runs full Pippenger on its slice. Limited by core count + memory bandwidth.

GPU (WebGPU)

~10,000+ threads

Pipeline split into stages, each stage massively parallel. Limited by per-thread compute & field-mul cost.

Trade-off: GPU per-thread arithmetic is $\sim 25\times$ slower than native — but parallelism wins at scale.

WebGPU execution model

Dispatch = 3-D grid of workgroups. Each workgroup = fixed grid of threads.

dispatch(x=4, y=1, z=1)
workgroup [0, 0, 0]
workgroup [1, 0, 0]
workgroup [2, 0, 0]
workgroup [3, 0, 0]
  • Threads in same workgroup share workgroup memory & can workgroupBarrier().
  • Threads across workgroups: independent, no sync.
  • Pipeline = compiled WGSL shader + bind-group layout. Built once, dispatched many times.

Memory model + the persistent context trick

Storage buffers
Large (GBs), R/W from shaders. Where the bulk MSM state lives: point coords, scalars, bucket sums, scratch arrays.
Uniform buffers
Small (≤ 16 KiB), R-only. Used for kernel parameters: $n$, $T$, $c$, num-subtasks, etc.
Bind groups
Bind a set of buffers to a pipeline's slots. WebGPU requires them to be re-created when the underlying GPUBuffer identity changes.
Persistent GpuContext — the big perf win
One GPUDevice, cached pipelines, cached buffers (keyed by curve + chunk_size + $n$), cached bind groups. Across 20–50 MSMs in a Honk proof, per-call overhead drops from $\sim 200$ ms (cold) to $\sim 0$.
CachedBases
SRS uploaded & converted to Montgomery form once. Subsequent MSMs only upload scalars ($n \cdot 32$ B), not points ($n \cdot 64$ B + Stage-1 Barrett/Montgomery).

The cuZK paradigm — MSM as sparse $M \cdot \mathbf{P}$

View the digit decomposition as a $T \times n$ incidence matrix:

$$ M_{j,i} \;=\; \begin{cases} s_{i,j} & \text{if } s_{i,j} \neq 0 \\ 0 & \text{else}\end{cases} $$

Then the MSM splits as:

$$ S \;=\; \sum_j 2^{jc}\, W_j, \qquad W_j \;=\; \sum_{i=0}^{n-1} M_{j,i}\, P_i $$

Each $W_j$ is a sparse matrix-vector product. Group columns by digit value (= CSC representation) and the inner loop becomes parallelisable per-bucket.

Key insight: MSM ≡ "transpose, then accumulate".

5-stage pipeline

Stage 1 — decompose_scalars_only
scalars ($n \cdot 32$ B) → digit chunks ($T \cdot n$ u32)  ·  1 dispatch, $n$ threads
↓
Stage 2 — parallel transpose (CSR → CSC)
3 dispatches: count, scan, scatter  ·  $\Theta(Tn)$ threads
↓
Stage 3 — batch-affine SMVP
init → [schedule, inverse, apply] × MAX_ROUNDS → finalize  ·  per-round parallel over buckets / pairs
↓
Stage 4 — BPR (Bucket Points Reduction)
Parallel suffix-sum: $W$ threads per window  ·  $T \cdot W$ threads
↓
Stage 5 — subtask_reduce (Horner on GPU)
Single workgroup, $T$ threads, $c(T{-}1)$ doublings + $(T{-}1)$ adds. CPU reads back $\sim 240$ bytes.

Stage 1: Decompose scalars

Per-thread work:

$$ \text{chunks}[t \cdot n + i] \;=\; \text{signed\_slice}_t(s_i),\quad t \in [0, T) $$

Each thread reads one scalar ($32$ B), writes $T$ digits. One dispatch, $n$ threads.

t0 t1 t2 t3 t4 t5 t6 t7 … tₙ₋₁
$n$ threads in parallel — each owns one scalar $s_i$

Warm-path optimisation: each thread also atomicAdds into col_ptr for its digit → fuses Stage-1 with Stage-2a's count phase. Saves $\sim 3$ ms at $n = 2^{16}$.

Stage 2: Parallel transpose

After Stage 1, the digit array is in CSR order (grouped by window/row).

Stage 3 needs CSC order (grouped by bucket/column). Hence the transpose.

CPU bberg: MSD radix sort

One-pass, in-place, 8-bit radix. Cache-friendly, sequential.

GPU: 3-phase parallel

Atomic counts → prefix scan → atomic scatter. 3 dispatches, $\Theta(Tn)$ threads each.

Same end result; very different memory access patterns. (↓ for each phase)

2a Count phase

For each $(i, t)$, atomically increment col_count[t·(B+1) + chunks[t·n+i] + 1].

t0 t1 t2 t3 t4 t5 t6 t7
all $n$ threads atomicAdd in parallel

Output buffer col_count[t·(B+1)]: count of each bucket's occurrences within each window.

⚠ Atomic contention possible when multiple threads hit the same bucket — but spread is wide for random scalars.

2b Prefix scan phase

Exclusive prefix sum on col_count within each window.

$$ \texttt{col\_ptr}[t \cdot (B{+}1) + b] \;=\; \sum_{k < b} \texttt{col\_count}[t \cdot (B{+}1) + k] $$

Gives the start position of each bucket in the final val_idx array.

b₀ b₁ b₂ b₃ b₄ b₅ b₆ b₇
$B$ threads per window, Hillis-Steele $\log_2 B$-depth scan

One dispatch per window (or fused across windows), $B$ threads per workgroup.

2c Scatter phase

Each thread (one per CSR entry) writes its point_idx to the right slot in val_idx.

$$ \texttt{pos} = \texttt{atomicAdd}(\texttt{current}[t \cdot B + k], 1) $$ $$ \texttt{val\_idx}[t \cdot n + \texttt{col\_ptr}[t \cdot (B{+}1) + k] + \texttt{pos}] = i $$

t0 t1 t2 t3 t4 t5 t6 t7
$n$ threads write in parallel — each owns one CSR entry

Output: val_idx = point indices, grouped by bucket. Same end result as bberg's MSD radix sort.

Stage 3: Batch-affine SMVP — rounds, not recirculation

CPU bberg: recirculation

  1. Walk sorted schedule
  2. 4-case classifier; queue pairs
  3. Batch invert when scratch full
  4. Feed outputs back through classifier
  5. Repeat until empty

↺ Inherently sequential

GPU: rounds

  1. Init: seed running sums per bucket
  2. For round = 0 .. MAX_ROUNDS:
    • schedule: each active bucket queues its next pair
    • parallel batch invert all queued deltas
    • parallel apply to running sums
  3. Finalize: pack into Jacobian + signed-neg

∥ Each step is parallel

Same affine trick math; very different control flow. GPU trades extra dispatches for full parallelism within each step.

3a Init

One thread per bucket. For each non-empty bucket $b$:

  • running[b] ← P[val_idx[row_begin[b]]]   (first point in bucket)
  • cursor[b] ← row_begin[b] + 1
  • active[b] ← cursor[b] < row_end[b]

Empty bucket: cursor[b] ← row_end[b], active[b] ← 0 (skipped from now on).

b0 b1 b2 b3 b4 b5 b6 b7
$B$ threads — active/idle based on bucket emptiness

3b Schedule (per round)

Each active bucket queues the next pair: (running[b], P[val_idx[cursor[b]]]).

fn schedule(b: u32) {
  if cursor[b] < row_end[b] && active[b] {
    let next_pt = P[val_idx[cursor[b]]];
    let delta = next_pt.x - running[b].x;
    let pos = atomicAdd(&pair_counter, 1u);
    pair_delta[pos] = delta;
    pair_meta[pos] = b;     // remember target
    cursor[b] += 1;
  }
}

$\sim B$ threads run; only buckets with $\geq 2$ pending points actually queue.

Output: a packed array of $m$ independent pair-deltas, ready for one big batch invert.

3c Batch inverse (parallel)

Compute $m$ inverses sharing one Fermat inversion. Adapted Montgomery prefix-product:

$$ \pi_k = \delta_0 \delta_1 \cdots \delta_k, \quad \rho_m = \pi_m^{-1} \quad\textit{(1 inv)} $$

$$ \delta_k^{-1} = \rho_{k+1} \cdot \pi_{k-1}, \quad \rho_{k-1} = \rho_k \cdot \delta_k $$

Multi-workgroup mode: $m$ deltas split into NUM_SUB_WGS slices, each independently inverted by a workgroup of 64 threads.

⚠ This stage is the dominant cost at large $n$ (47% of GPU wall at $2^{20}$). The per-workgroup Fermat inversion stays sequential.

3d Apply (parallel)

One thread per pair. Read $(P, Q, \delta^{-1})$ from the pair pool; compute affine sum; write to running[target].

$$ \mu = (Q_y - P_y) \cdot \delta^{-1},\quad R_x = \mu^2 - P_x - Q_x,\quad R_y = \mu(P_x - R_x) - P_y $$

p0 p1 p2 … pₘ₋₁
$m$ threads, one per queued pair — fully parallel

Cost per pair: $\sim 3 \,|M| + |I|/m$. With $m = 1024$, $|I| \approx 332 |M|$: $\sim 3.3 |M|$ per pair.

After apply: running[] has each bucket's partial sum, ready for the next round.

3e Finalize

After MAX_ROUNDS, pack each bucket's running affine sum into Jacobian $(X, Y, Z{=}R)$ for downstream BPR:

$$ \texttt{bucket\_x[b]} \leftarrow \texttt{running\_x[b]}, \quad \texttt{bucket\_y[b]} \leftarrow \texttt{running\_y[b]},\quad \texttt{bucket\_z[b]} \leftarrow R $$

Apply signed-digit negation: $-(x, y) = (x, -y)$ for negative-bucket entries.

Buckets that had a final unflushed pair go through a 2-pass finalize (collect → batch invert → apply).

b0 b1 b2 b3 b4 b5 b6 b7
$B$ threads in parallel — finalize

Stage 4: BPR — parallel suffix-sum

For each window $j$, compute $W_j = \sum_k k \cdot B_{j,k}$. Same math as the CPU bberg suffix-sum, parallelised.

Strategy: split $B$ buckets among $W$ threads per window

// per-thread, slice of B/W buckets
thread t handles  k ∈ [t · B/W, (t+1) · B/W)

// Each computes a local (m_partial, g_partial)
m_t = sum of B[k] for k in slice
g_t = thread t's contribution to g, AS IF
      thread t were the only thread

// BPR-2 combines W threads:
// every thread's g_t needs the "carry"
// from threads with higher slices.

Total: $T \cdot W$ threads (e.g. $17 \times 256 \approx 4{,}352$ at $n = 2^{16}$).

⚠ At small $n$, BPR-1 dominates (37% of GPU wall at $n{=}2^{16}$). Cost is independent of $n$ — scales with $B = 2^{c-1}$.

Stage 5: Horner on GPU

Combine the $T$ window points $W_0, \ldots, W_{T-1}$ into the final $S$:

$$ S \;=\; W_0 \;+\; 2^c\, W_1 \;+\; 2^{2c}\, W_2 \;+\; \cdots \;+\; 2^{(T-1)c}\, W_{T-1} $$

Single workgroup, $T$ threads:

  1. Each thread reads its window sum $W_j$ into workgroup memory
  2. workgroupBarrier()
  3. Thread 0 walks the Horner chain: $c$ doublings + 1 add per step, $T{-}1$ steps total
  4. Thread 0 writes result $(X, Y, Z)$ to result_xyz[0]

For $T = 17$, $c = 15$: $\;240$ doublings $+$ $16$ adds $\approx 4{,}000$ field ops.

CPU reads back $\sim 240$ B (one Jacobian point), normalises to affine, returns.

Key design choices

$c = 15$ (not the textbook $c = 14$)
BPR-1 cost $\propto T \cdot B = T \cdot 2^{c-1}$. At $c{=}15$: $17 \cdot 2^{14} = 278{,}528$. At $c{=}16$: $16 \cdot 2^{15} = 524{,}288$ — 1.88× more. Stage-1/2/3 costs change marginally. Empirical sweet spot.
13-bit limbs ($L = 20$)
WGSL has u32 only. For $u32 \times u32$ accumulator safety: $2w + \lceil \log_2 L \rceil \leq 32$. Solving: $13 + 13 + 5 = 31$ ✓, but $14 + 14 + 5 = 33$ ✗. $w = 13$ is the max safe width on WGSL.
Persistent context + cached bases
Cold path: $\sim 200$ ms per MSM (device + shaders + Stage-1). Warm: bases pre-converted, pipelines cached, buffers reused. Per-call cost down to $\sim 70$ ms at $n=2^{16}$.
Batch-affine over Jacobian mixed-add
Mixed-add: $\sim 11\,|M|$ per add. Batch-affine: $\sim 3.3\,|M|$. $\sim 3.3\times$ on the hottest path.
Rounds over recirculation
Recirculation is sequential; GPU thrives on parallel-within-step. Trade extra dispatches for full inner parallelism.

Where WebGPU shines

  • Stage 1 — $n$ scalars decomposed in 1 dispatch. CPU bberg interleaves digit extraction with each window.
  • Stage 2 scatter — $n$ parallel atomic writes. CPU bberg radix-sorts sequentially.
  • Stage 3 schedule/apply — up to $\sim B$ pairs queued and applied per round, fully parallel. CPU bberg processes pairs sequentially through the classifier.
  • Stage 4 BPR — $T \cdot W$ threads cooperate. CPU bberg walks each window's buckets sequentially.

Wider $n$ means more work per stage to amortise the fixed cost of kernel launches and shader pipelining. Speedup grows with $n$.

Bottleneck 1: ba_inverse

$47\%$ of GPU wall at $n = 2^{20}$. Grows linearly with $n$.

What it does
Per round, batch-inverts $m$ pair-deltas. Multi-workgroup parallel mode: $m$ deltas split into $\texttt{NUM\_SUB\_WGS}$ slices.
Why it's slow
Each workgroup runs a sequential Fermat inversion ($\sim 254$ squarings + multiplies). Many rounds → many such inversions.
How to improve
  • Increase $\texttt{NUM\_SUB\_WGS}$ at large $n$ (more SM occupancy, more inversion concurrency)
  • Reduce MAX_ROUNDS by packing more pairs per round
  • Explore Bos–Coster style batch inversion (slightly different math)

Predicted: $2\times$ improvement here → wall drops from 397 ms to $\sim 280$ ms at $n = 2^{20}$.

Bottleneck 2: ba_apply

$21\%$ of GPU wall at $n = 2^{20}$. Grows linearly with $n$.

What it does
$m$ threads compute parallel affine adds: $\mu, x_3, y_3$ formulas. Reads pair-deltas, $\delta^{-1}$, $P, Q$ coords; writes updated running[b].
Why it's slow
Likely memory-bandwidth bound: each thread reads $\sim 2 \times 20 \times 4 = 160$ B of BigInt coords. At $n = 2^{20}$, that's $\sim 200$ MB of buffer traffic per round.
How to confirm + fix
  • Run the roofline microbench (gen_roofline_microbench_shader) to compare BW vs compute throughput
  • If BW-bound: convert AoS pair pool → SoA (split-coord arrays)
  • Bigger limb width ($w = 13 \to 16$, $L = 20 \to 16$) → 20% BW saving but needs WGSL carry redo

Bottleneck 3: bpr_1

$37\%$ at $n = 2^{16}$; only $8\%$ at $n = 2^{20}$. Cost is fixed in $n$ (scales with $B = 2^{c-1}$).

What it does
Per-window parallel suffix-sum reduce: $W$ threads compute local $(m_t, g_t)$ partials over slices of $B/W$ buckets each.
Why it's slow at small $n$
$B \cdot T$ work is constant ($\sim 280{,}000$ G$_1$ adds with $c = 15$). At small $n$, this fixed cost is the largest fraction.
Free / cheap wins
  • bpr_inner_loop = "mixed_safe" — saves $\sim 8$ ms (10% on $n=2^{16}$ wall). Already in the library.
  • bpr_inner_loop = "assume_affine" — saves $\sim 13$–$25$ ms (Tint codegen sensitive).

These knobs are 1 parameter at the entry point. Try them first.

Optimization roadmap (ranked)

Tier 1 — bpr_inner_loop variants
Already in the lib. Flip default. 10–25% win at $n = 2^{16}$, low risk.
Tier 2 — ba_inverse parallelism budget
Tune NUM_SUB_WGS as function of $n$. Re-tune MAX_ROUNDS. Potential $2\times$ on large $n$.
Tier 3 — roofline ba_apply
Microbench BW vs compute. If BW-bound, SoA + limb-width refactor. 20% saving possible.
Tier 4 — GLV / endomorphism
Decompose 254-bit scalars into two 128-bit halves using bn254's $\phi$. Halves $T$. Big algorithmic lever. Removed from current code; needs re-wire.
Tier 5 — Hide writeBuffer(scalars)
CPU upload is sync today (~15 ms at $n = 2^{20}$). Overlap with previous dispatch.

Specialized scalar distributions

Case A: 32-bit scalars

$T = \lceil 32/c \rceil$ drops from 17 to 2 (or 3). All linear stages shrink by $\sim 8\times$. BPR-1 shrinks by 8×.

Modelled: $n=2^{16}$ wall 75 → 14 ms (5.4× speedup).

Case B: 90% zero, 10% small

Current pipeline gains nothing — every stage iterates over $n$ regardless of sparsity.

Need a zero-filter compaction front-end (one pass + atomicAdd to produce a list of nonzero scalars).

Modelled (with zero-filter + small $c$): $n=2^{16}$ wall 75 → 5–8 ms (10–15× speedup).

Both require new entry points but the underlying shaders are unchanged. The infrastructure (glv_override shape) exists.

Takeaways

  1. WebGPU MSM is a different shape of the same Pippenger: rounds over recirculation, parallel transpose over radix sort, parallel BPR over sequential suffix-sum.
  2. It pays $\sim 25\times$ per-thread field-mul cost vs native, and wins by running $\sim 10^4$ threads in parallel.
  3. Persistent context + cached bases are load-bearing: without them the cold-path cost dominates.
  4. At $n = 2^{20}$ we're 2.06× faster than 14-thread WASM-MT. The speedup grows with $n$.
  5. Two dominant stages: ba_inverse (linear in $n$) and bpr_1 (flat in $n$). Optimisation strategy depends on which $n$ matters.
  6. For sparse / small-scalar workloads, a sparse-aware front-end can deliver 10–15× on top of the current pipeline.
