# Test Framework Refactoring: Unifying Tampering and WitnessOverride

**Date**: 2025-11-03
**Status**: Explored, not yet merged
**Files affected**: `test_class_predicate.hpp`, `multi_scalar_mul.test.cpp`, `ec_operations.test.cpp`, `ecdsa_constraints.test.cpp`

## Problem Identified

The current test framework has two separate classes for witness invalidation:
- **`Tampering`**: Invalidates output/result witnesses
- **`WitnessOverride`**: Invalidates input witnesses

**Issue**: Both classes do the same thing (invalidate witnesses) but are artificially separated. This creates:
1. Confusing mutual exclusivity logic
2. Duplicate code patterns
3. Unclear semantics (why is invalidating an output different from invalidating an input?)

### Current Pattern Example (MultiScalarMul)
```cpp
class Tampering {
    enum class Mode : uint8_t { None, Result };
    // ...
};

class WitnessOverride {
    enum class Case : uint8_t { None, Points, Scalars };
    // ...
};

static void tampering(constraint, witness_values, tampering_mode) { ... }
static void override_witness(constraint, witness_values, witness_override) { ... }
```

### Usage Logic
```cpp
// In test_witness_false:
auto tampering_mode = override_case == WitnessOverrideCase::None
                        ? default_tampering_mode    // Use Tampering
                        : TamperingMode::None;       // Use WitnessOverride
```

This is convoluted! You use one OR the other, never both.

## Proposed Solution

### Unified Pattern
```cpp
class InvalidWitness {
    enum class Target : uint8_t { None, Points, Scalars, Result };
    // Single enum for ALL witness invalidation targets
};

static void invalidate_witness(constraint, witness_values, invalid_witness_target) {
    // Single method handles all cases
}
```

### Benefits
1. **Clarity**: One concept = one class. "Invalidate witness at target X"
2. **Simplicity**: No mutual exclusivity logic needed
3. **Semantics**: From constraint perspective, all witness invalidation is the same
4. **Maintainability**: Single invalidation method to maintain

## Implementation Changes

### 1. test_class_predicate.hpp
```cpp
// OLD
typename T::Tampering;
typename T::Tampering::Mode;
typename T::WitnessOverride;
typename T::WitnessOverride::Case;
{ T::override_witness(...) } -> std::same_as<void>;
{ T::tampering(...) } -> std::same_as<void>;

// NEW
typename T::InvalidWitness;
typename T::InvalidWitness::Target;
{ T::invalidate_witness(...) } -> std::same_as<void>;
```

### 2. Constraint Test Files
Each constraint defines `InvalidWitness::Target` appropriate for its inputs/outputs:

**MultiScalarMul**:
- `None, Points, Scalars, Result`

**EcAdd**:
- `None, Input1, Input2, Result`

**ECDSA**:
- `None, R, ZeroS, HighS, P, Result`

### 3. Test Method Renames
```cpp
// OLD
test_tampering() -> tests all Tampering modes

// NEW
test_invalid_witnesses() -> tests all InvalidWitness targets
```

## Why Not Merged Yet

User wants to review the conceptual change before committing. The separation may have been intentional for semantic reasons not immediately obvious from the code.

## Key Insight

From the constraint's perspective:
```
if (predicate == true) {
    constraint_equation_must_hold();  // Any invalid witness fails
}
if (predicate == false) {
    skip_constraint();  // Any invalid witness is OK
}
```

There's no semantic difference between invalidating inputs vs outputs - both test the same predicate behavior. The separation was organizational, not logical.
